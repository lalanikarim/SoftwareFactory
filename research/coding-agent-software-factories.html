1 What a "software factory" is

A managed system for producing software with repeatable inputs, standardized tooling, measurable output, and enough retained context to reconstruct how any change was made.

The core distinction from a coding assistant

The factory is the process around the agents. Agents are the workers; intake → prepared environments → implementation → independent review → end-to-end verification → feedback loop → human approval is the production line. Work starts from tickets, alerts, webhooks, or schedules — not a human pasting a prompt. The agent runs unattended on a machine with your real stack and returns a PR with evidence attached. Humans own the merge.

Four defining properties

Repeatable inputs

Work arrives as tickets, issues, alerts, webhooks, schedules — not a human remembering to trigger it.

Standardized tooling & environments

Each run gets an isolated machine with the real stack: repo, dependencies, env vars, database, services. Stays up for hours so long tasks don't die.

Measurable output

Cost per run, acceptance rate, human-intervention frequency — tied to delivery outcomes, not code volume.

Replayability

Starting revision, environment definition, task constraints, model config, commands, and the resulting patch are preserved so any shipped change can be reconstructed.

Historical roots

  • Robert Bemer — "software factory" at General Electric (late 1960s)
  • Hitachi Software Works (1969)
  • Michael Cusumano, Japan's Software Factories (1991) — Japanese firms organizing software production around reusable methods and tools
  • The agent-native variant extends old automation (build/test/deploy) into the investigation and implementation itself

2 Anatomy: layers of a factory

Islo's framework (from 100+ conversations with engineering teams): compute, security, orchestration, harnesses. Warp's integration model specifies the five pieces to connect:

PieceWhat it is
IntakeEvent-based trigger: GitHub label, Linear/Jira status change, Slack mention, PagerDuty alert, cron, webhook. Work starts without a person remembering.
RuntimeGoverned cloud environment scoped to repo + task; isolated machine per run that stays up for hours. No standing laptop-level access.
Defined roleOne stage of the SDLC per invocation: triage, implementation, review, or verification — not one agent doing everything ad hoc.
Handoff & checkpointOutput goes to a human approval before merge, or to the next agent in the pipeline (implementation → review).
MeasurementCost per run, acceptance rate, intervention frequency — separate from whether the agent is "smart."

The feedback loop (Factory 2.0 framing)

Bug reports, conversations, customer feedback, and requirements become planned changes → built, tested, reviewed, secured, shipped → monitoring the deployed software supplies the next signals. A deployment failure should lead to a reproducible test; an incident should be traceable to the relevant revision and configuration.

Three requirements for the loop Model independence — model choice can change with the task.  ·  Sovereign intelligence — control over the system and accumulated knowledge; data placement per deployment (managed / regional / airgapped).  ·  Continual learning — findings flow across stages: an incident improves a test or review instruction. "A software factory should learn from shipped work."

3 Evolution timeline (2019 → Feb 2026)

Per Ulderico Cirello's "The Evolution of AI Factories" — ten phases, from autocomplete to lights-out development.

2019 – 2023
Code completion → "AI pair programmer"

Tabnine, Kite → GitHub Copilot (June 2021), Cursor (Jan 2023), Windsurf "agentic IDE" (Nov 2024). AI as collaborative partner, line-by-line to whole-file.

Early 2023
Autonomous agent experiments

GPT-4 (Mar 2023), AutoGPT, BabyAGI. Proved the concept; revealed autonomy alone is insufficient — orchestration would be essential.

2024 – mid-2025
Agent swarms — "just throw tokens at the problem"

Devin AI (Cognition, Mar 12 2024) — first commercial "fully autonomous AI software engineer." Factory AI GA (May 28 2025). 8090 AI (Chamath Palihapitiya, Sep 2025). Constrained by context windows; worked in demos, struggled in production.

Feb – Jul 2025
Foundation model breakthrough

Claude Code research preview (Feb 24 2025, GA May 22). GPT-5 (Jul 24 2025) with 256K context — the "OH SHIT, I CAN USE THIS" moment. Multi-file, multi-agent workflows became viable.

Jul – Oct 2025
Agent management tools

VibeKanban (kanban board for agents; >50% of its own code agent-written), Conductor (Mac-native, git worktrees per agent), OpenAI Codex app ("command center," Feb 2 2026). Humans orchestrate agent teams.

Oct 2025 – Jan 2026
The technique revolution — Ralph Wiggums

Geoffrey Huntley's bash loop feeds an agent's output (errors included) back into itself until a stop condition. Each iteration is a fresh session; state lives in git history. Cited: $50k contract for $297 API cost. "Persistence matters more than sophistication." Spawned Loopy, Laravel Ralph, and the "everything is a ralph loop" meme.

Jan 2026
True orchestrators — the first factories

GasTown (Steve Yegge, Jan 1 2026): 20–30 parallel Claude Code instances in isolated git worktrees; "Hook" system enforces autonomous execution ("If there is work on your Hook, YOU MUST RUN IT"); a "CNC machine for code." Also Claude Flow (64-agent orchestration) and Sgai (single GOAL.md file + dashboard).

Feb 2026
Dark factories — humans out of the loop

Attractor (StrongDM, ~Feb 7 2026): released as NLSpecs (natural-language specs for building your own factory), not code. DOT/Graphviz pipeline runner; an agent writes implementation while a verification system runs thousands of tests, iterating until convergence. "Lights-out" development — humans banned from writing code.

Key insight across the timeline Coordination matters more than raw agent capability. The bottleneck moves — faster patch creation exposes missing tests, slow environments, and limited review capacity.

5 Design principles & best practices

Synthesized across Factory, Islo, and Warp's published guidance.

1 · Start with one easy-to-verify workflow

Bounded objective, known dependencies, testable result, human approval. Usually nightly regression or a single PR-review loop. Expand once you trust what it returns.

2 · Defined role before more autonomy

The #1 mistake is skipping straight to "let it merge on its own." A bounded task + human checkpoint first.

3 · Don't standardize too early

Don't lock into one model/harness before measuring which performs best on your codebase. Keep model choice per-task.

4 · Verify with the real stack

Tests run against services that are actually up; drive a real browser when needed. "A change that only compiles does not count as done."

5 · Evidence travels with the diff

Test output, recordings, gateway logs, audit trails — review is reading, not re-running. Wrong answers become cheap to diagnose.

6 · Humans own the merge

Blast radius = whatever your existing review process already allows.

7 · Measure outcomes, not code volume

Cost per run, acceptance rate, intervention frequency. Distinguish time generating a patch from time correcting/reviewing it.

8 · Fix the repo before scaling agents

Missing tests, slow environments, ambiguous instructions are what break agent runs. "More sessions will not repair a validation process that cannot distinguish a correct change from a plausible one."

9 · Close the feedback loop

Same mistake recurs → turn it into a test, maintained instruction (AGENTS.md), or enforced check. Setup fails repeatedly → repair the environment before increasing volume.

10 · Replayability is a requirement

Preserve revision, env definition, constraints, model config, commands, patch. OpenTelemetry export alone isn't enough.

11 · Least privilege for agents

Scope files, commands, networks, credentials to what each task needs; governed runtime instead of standing developer access.

7 Open questions & critiques

  • Autonomy vs. marketing claims — Devin's launch raised the bar for "fully autonomous"; skepticism persists about what autonomy actually means in production.
  • Do dark factories work at scale? Attractor pushes humans fully out of the loop; unproven beyond StrongDM's own use.
  • The bottleneck moves — patch generation gets cheaper, so review capacity, test coverage, and environment speed become the constraints.
  • Standardization risk — locking into one vendor/model early; the counter-trend is model/harness independence (Factory, Warp explicitly).
  • Data residency & sovereignty — where sessions, inference, and telemetry live matters for regulated industries; airgapped/on-prem offerings are a differentiator.
  • 8090 as cautionary tale — AI branding on requirements management isn't a factory; the process around agents is what matters.

8 Feasibility: building a factory on Pi Durable

Assessment of @earendil-works/pi-durable (Earendil's experimental durable agent harness) as the foundation for a personal-scale software factory. Full write-up: research/pi-durable-feasibility.md.

Verdict — highly feasible Every core factory primitive is a Pi Durable first-class feature, and the companion PoC (../engram/) verified nearly all of them under crash conditions, not just happy paths. What remains is glue work (ticket/PR integration, evidence packaging, CI gating) plus two structural risks: local-model quality on long-horizon coding and the experimental API.

11/11 factory requirements have a verified or native mechanism; 9 are crash-tested. Pi Durable's replayability guarantees are arguably stronger than what commercial factories advertise — and the whole source is ~15k lines, readable by an agent.

Gaps to close (glue work, days each)

  1. GitHub/ticket integration — issue webhook → submit({requestId: issue-id}); approval-gated PR create/update tool. Unbuilt; patterns proven.
  2. Evidence packager — diff + test output + transcript excerpts → PR comment. Data already in committed state.
  3. Reviewer role config — read-only tools + test execution, own checkout (the PoC subagent pattern already runs this exact shape).
  4. CI gate — consume the structuredOutput verdict; block merge on fail.
  5. Measurement dashboard — acceptance rate + tokens per task from pi.usage.

Single-owner storage (no built-in HA)Low–MedOne process per agent is fine at this scale; Postgres-backed custom backend if failover needed.

Recommended path

Phase A · ~2 weeks
Build the engram MVP first

Telegram + Web UI, web fetch, sandboxed local code gen/test, approval gates. Not detour work — every primitive it exercises is a factory component.

Phase B · ~1–2 weeks
Add the factory layer (glue)

GitHub tools, reviewer subagent role, evidence packager, CI gate, measurement. Start with one easy-to-verify workflow — e.g., "issue → PR on a single repo, bounded scope" — and measure acceptance rate before adding stages.

Phase C · when needed
Scale decisions

Postgres-backed storage for HA, model pool (Ollama small models), optional cloud provider for hard tasks, browser automation in the sandbox.

Bottom line At personal scale, a working single-repo software factory is a few weeks of glue away from the current PoC state. The binding constraints are model quality and inference throughput on local hardware — not the harness.
