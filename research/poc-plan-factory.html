1 Context

Three prior bodies of work make this plan possible — and define exactly what this PoC must (and must not) test.

Already proven (do not re-test)

The companion Pi Durable PoC (../PiDurable/) verified, under crash conditions: SIGKILL→resume recovery · exactly-once submissions (requestId) · crash-durable approval gates · sandboxed per-conversation execution (Podman) · lossless SSE streaming · subagent fan-out with role-scoped tools · compaction on a local model · 100%-success benchmark battery on Qwen3.8-27B (IQ3_S GGUF) via Unsloth on an RTX 4090.

1a Phase 0 results (2026-10-19)

Gate G0 — pass · 8/8 checks · no GPU required node poc-factory/01-intake-g0.mjs: agent-labeled issue event starts exactly one submission (requestId = issue-<n>) · simulated double-delivery (new X-GitHub-Delivery, same issue) yields no second run — the same submission is returned · events without the agent label are not forwarded · late agent label on a processed issue re-submits to the same run · issue content, including seeded prompt-injection text, is confined to <untrusted> delimiters with the do-not-follow wrapper outside them · JSONL audit log records every event (replayable intake) · pure intake helpers behave as specified.

Design decision (F1 resolved)

The adapter is deliberately stateless w.r.t. retries: GitHub redeliveries carry new delivery ids but the same issue, so exactly-once holds at the durable server's submit() via the client-chosen requestId (crash-verified in ../PiDurable/poc/02-durable.mjs, PHASE2-DUP). The adapter keeps a JSONL audit log for replayability rather than its own dedup state.

2 Goal & non-goals

Goal Demonstrate a single-repo factory loop end-to-end: a GitHub issue is picked up automatically, a sandboxed worker agent produces a branch + draft PR, an independent reviewer role verifies it with a machine-readable verdict, evidence (diff summary, test output, transcript excerpts) is attached to the PR, and a human approves the merge via Telegram or web — surviving a crash at every stage without duplicate effects.

Non-goals (deferred)

  • Multi-repo coordination, cross-repo dependency ordering
  • HA / failover, Postgres-backed storage, multi-Pod scaling
  • Running N issues in parallel (throughput is measured, not engineered)
  • Browser automation, email client, MCP bridge
  • Auto-merge — the human checkpoint is a factory requirement, not a PoC limitation

5 Phases & gates

Six gated phases plus a measurement phase. Gates are objective — no model judgment calls on pass/fail.

0

Fixture & intake wiring

  • Setup: small private GitHub fixture repo (~500-line Node/Python service) with a working test suite. Seed four issues: three bounded, well-specified tasks + one trap (an issue where the obvious fix is subtly wrong).
  • Intake: webhook adapter maps issues event with label agent → POST /tasks { content: <issue as <untrusted> data>, requestId: "issue-<n>" }.
  • Tests: open issue #1 → exactly one run. Simulate webhook double-delivery → no second run, same submission returned. Verify issue text enters the transcript as delimited untrusted data.
Gate G0: exactly-once intake under simulated retry; issue content enters as data, not instructions.
1

Intake & orchestration

  • Issue #1 flows unattended: orchestrator reads the issue, plans, spawns the worker subagent in the sandbox on branch agent/issue-1, and the worker produces a commit + draft PR (merge stays gated).
Gate G1: a real issue yields a draft PR with no human intervention between webhook and PR creation.
2

Worker quality

⚠️ the key risk
  • Run all three good issues end-to-end. Objective checks per issue (no model judgment): test suite passes on the resulting branch · diff scoped to the issue (≤ 3 files outside obvious scope) · the specific behavior named in the issue is fixed (fixture issues are chosen so this is script-checkable).
Gate G2: ≥ 2 of 3 issues produce a passing, scoped PR with zero human edits. This acceptance rate decides whether local models can hold the implementation role.
3

Independent reviewer — the negative test matters

  • Reviewer subagent: own checkout of the worker's branch, read-only tools + bash restricted to the test suite; emits structuredOutput { verdict: pass|fail, evidence[], concerns[] }.
  • Negative test (the one that counts): on the trap issue's worker output → must return fail with a reason pointing at the actual bug, not a superficial complaint.
  • Positive control: known-good branch → pass without spurious concerns. Orchestrator branches on the verdict (fail → file findings, no merge PR).
Gate G3: trap caught with correct reason; good branch passed. A reviewer that passes everything fails this gate by definition.
4

Evidence & human checkpoint

  • Evidence packager: on reviewer pass, assemble the PR description (diff summary, test output, transcript excerpts, reviewer verdict). Verify all sections present.
  • Merge gate: gh pr merge tool is approval-gated; approve via Telegram inline button → merge executes.
  • Crash test: SIGKILL the factory process while merge-approval is pending → restart → approve → merge executes exactly once (one merge commit, no duplicate PR state).
Gate G4: evidence complete on the PR; exactly-once merge across crash. Failure here stops the PoC — an exactly-once violation with real side effects.
5

Feedback loop

  • Take a concrete reviewer finding from Phases 2–3 (e.g., "worker didn't add a regression test"). Orchestrator records the lesson in its instructions document (or files a follow-up task). Re-run the same or analogous issue → the corrected behavior appears (regression test present this time).
Gate G5: one concrete, verifiable instance of "the same mistake doesn't recur." This is the difference between an agent runner and a factory.
6

Measurement & sizing

  • Collect per issue: tokens in/out (pi.usage doc), wall time, tool-call count, self-corrected errors, human interventions, acceptance (passed G2 checks without edits).
  • Compare against the existing PoC's toy-battery numbers (medians 2.2s / 5.1s / 13.2s per turn) to size real tasks.
No gate. This data drives later decisions: model pool, optional cloud provider for the worker role, overnight batch throughput on one GPU.

6 Decision points & fallbacks

Every gate failure has a pre-decided, actionable response — no ad-hoc judgment at the moment of failure.

TriggerDecision / fallback
G2 < 2/3 acceptanceLocal models not ready for the implementation role. Options in order: (1) stronger local model if hardware allows; (2) cloud provider for the worker role only — provider config is per-conversation and swappable, no re-architecture; (3) descope the factory to triage + review with human implementation.
G3 misses the trap after instruction tighteningAgent review becomes advisory (verdict posted on PR, human decides); keep building the loop, revisit with a stronger reviewer model later.
G4 double-merge or lost merge stateStop. Audit the approval/merge tool's idempotency design before anything else ships; this is the one failure that can't be papered over.
G5 no observable behavior changeFeedback loop stays manual (human updates instructions); the honest claim becomes "durable agent runner with review gates," not "self-improving factory."
Phase 6 latency/cost far above toy-battery expectationsRevisit role model assignments and batch cadence before scaling issue volume.

10 Conventions (carried into implementation)

  • Request IDs: issue-<n> for intake, job-<date>-<slug> for scheduled follow-ups — always client-chosen, never generated server-side, so retries are safe by construction.
  • Branch naming: agent/issue-<n>; one branch per issue; no force-push ever (a new attempt = a new branch).
  • Approval semantics: use per-execution nonces in the approval key (sha1(tool + args + nonce)), fixing the per-distinct-action persistence observed in the existing PoC — for a factory, re-running an approved merge must require fresh approval.
  • Untrusted input: issue titles/bodies/comments and all fetched content enter transcripts only inside <untrusted> delimiters; consuming roles get no write tools beyond their scoped duties.
  • Version pins: exact versions of pi-durable, pi-ai, chord recorded in the PoC's lockfile and in this plan's results write-up.
