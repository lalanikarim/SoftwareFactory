How Drydock Works

Drydock is a coding-agent software factory: GitHub issues go in, reviewed pull requests come out — unattended end to end, with humans keeping the final decision at merge. It runs on Pi Durable (durable conversations, sqlite storage, task scheduler, single-use approval documents); the implementation is ~4,000 lines of JavaScript in poc/.

Pipeline: tickets in → sandboxed implementation → independent review → evidence on the PR → approval-gated merge. Gates G0–G5 passed on a live fixture repo; drydock is itself its first managed repo (dogfooding). Markdown source of truth: research/drydock-explainer.md.

Exactly-once intake

Webhook redeliveries dedup at the durable server via stable requestId = "issue-N".

Untrusted data, delimited

Issue text only ever travels inside <untrusted> with a do-not-follow wrapper.

Humans own the merge

Single-use durable approvals; the agent can never self-approve or bypass the gate.

Intake & security

What the adapter checks, in order

Fig. 2 — Intake path (Fig. 1's first hop, expanded). Signatures are checked pre-parse, so the matching secret doubles as per-repo authorization; an event signed with repo A's secret naming repo B is rejected (gate M3). Non-loopback binds without a secret refuse to start. Every decision — accepted or rejected — lands in the JSONL audit log.

Implementation & review

The worker run and the reviewer gate

Worker (delegate, host-side prep before the model sees anything)

  1. Fetch the issue fresh via gh api (host, token from config/env).
  2. Prepare workspace work/issue-N/: fresh clone (--recurse-submodules), branch agent/issue-N, credential scrubbed from the remote URL — the worker never pushes.
  3. Setup phase (if configured): one-shot networked container installs deps; state persists via the host-mounted workspace. The agent itself never runs in a networked container.
  4. Sealed sandbox: one Podman container per conversation — node+git, network=none, no host env vars — torn down when the task settles.
  5. Deterministic prompt: issue inside <untrusted>, standing lessons in a trusted section, fixed working rules (smallest change, add tests, run the suite, commit only changed files).

Supervision: a per-issue wall-clock budget aborts cleanly on overrun (partial branch preserved for rework), and a sandbox-health probe before every exec detects dead containers and recreates them in place — no silent retry loops until the budget.

Reviewer (structurally read-only)

  • read — guarded file reads; git_diff — host-side diff vs merge base; run_tests — test suite inside the sandbox (untrusted test code never runs on the host); submit_verdict — machine-consumable {verdict, evidence, concerns}.
  • Judges whether the change actually satisfies the acceptance criteria — not just that the suite passes (the fixture's trap issue exists to catch "tests pass but criterion violated" fixes).
  • Refusal: no push, no PR; orchestrator records ≤1 lesson via note_lesson, then presents verdict + concerns. Pass: open_draft_pr host-verifies the suite, pushes (only its own factory branch, --force-with-lease), opens/refreshes the DRAFT PR with an evidence body. It never merges.
Phase 4 — the merge gate

Single-use durable approvals, exactly-once merge

Fig. 3 — The merge state machine. The approval record is a durable document (factory.merge-approval): written only by the human-facing POST /approvals, consumed only by the merge tool, single-use. Crash-safe either way — crash after consume but before the merge lands → the PR-state check makes a re-approved rerun a no-op (alreadyMerged). Verified under SIGKILL in gate G4.

Feedback & operations

Lessons, multi-repo fleet, supervision

Feedback loop (Phase 5)

  • Lessons live in a host-side file (data/lessons.md) — deliberately not a durable doc, because per-run sqlite databases are wiped between battery runs but lessons must outlive them.
  • Standing instruction: on every refused review, first note_lesson (one imperative sentence generalizing the finding), then present the finding. Every future worker prompt reads the file at spawn — trusted section, outside <untrusted>, subordinate to the issue's acceptance criteria.
  • Verified in G5: with no lessons a worker repeated a known handler-patch mistake; after one recorded lesson the re-run fixed the bug at the root (e.g. giving the error class a statusCode instead of patching the catch site).

Fleet operation

  • One adapter, N factories. The adapter is stateless (audit log only); dedup lives at each factory's durable server. The fleet file names one config + port + sqlite db per managed repo.
  • Per-repo config, validated at startup: repo identity, sandbox image, setupCommand/testCommand (argv-only — shell metacharacters rejected), budgets. Config file always wins over the legacy env fallback.
  • Fleet supervisor: starts every factory + adapter; restart-on-fault with backoff and a cap (safe because the durable harness recovers state from its sqlite db); status fans out to each factory's /health, /approvals, /tool-results.
  • Dogfooding: drydock is its own first managed repo (poc/config/lalanikarim-drydock.json) — setupCommand: npm ci --prefix poc, testCommand: node poc/01-intake-g0.mjs.

Design principles, in one breath

  1. SecurityUntrusted data is delimited and never executed; credentials stay host-side.
  2. DeterminismThe orchestrator is a fixed procedure with four tools — minimal model judgment in the plumbing.
  3. GatesEvery external write is host-side and gated; humans own the merge.
  4. DurabilityCrash-durability is first-class: exactly-once intake, crash-safe approvals, restart-on-fault — verified under SIGKILL.
  5. Fail closedSignature checks before parsing; 403 + audit line on every rejection; budgets that abort cleanly and preserve partial work.
